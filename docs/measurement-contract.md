# Measurement contract, CSV schema 2

The main OLSR random-graph study retains **one destination**, per the user's decision. The fixed seven-node/two-destination butterfly remains a separate prototype for correctness and the requested central-link rate comparison.

## Collection and timing

Both examples use `examples/experiment-metrics.h`. `PhyTxBegin` counts modeled PPP frames and their actual packet sizes on each directed point-to-point device. These byte totals include the modeled PPP header, IP/transport/application headers, data, control and retries. They exclude physical overhead not represented in ns-3's PPP packet. They are aggregate traffic cost across links, not capacity or end-to-end throughput. Control classification is specific to these applications: TCP payload versus control-only segments; OLSR UDP port 698; NC ACKs of 15 application bytes; remaining NC datagrams as data. Other protocols are grouped with control.

`offer_s` is the source's first application offer, including TCP connection setup: 1 s in the fixed example, 55 s in the current OLSR schedule. Routing traffic before that time appears in `pre_frames/pre_bytes`; subsequent routing frames are counted separately within transfer traffic. `deadline_s = simulationTime - cleanupTime`. Applications stop at that deadline, and the simulator continues through the cleanup interval. Frame totals include this drain interval and connection shutdown traffic started within it. Retries scheduled beyond simulation end are excluded; under losses this is bounded-horizon traffic cost, not guaranteed complete session-teardown cost. They are measured over the same horizon for both methods, independently of success. Sender/receiver application timestamps supply completion; simulation stop time is not completion time.

## Fields and missing values

- `useful_bytes`: unique verified payload at receivers, excluding all headers and duplicates. NC counts recovered originals; a directly received systematic original can count before full generation recovery. TCP counts validated stream payload without interpreting receive callbacks as original packet boundaries. Fixed-butterfly values sum across both receivers (4096 bytes at full completion); OLSR single-destination completion delivers 2048 bytes.
- `completed/required/success`: destination completion, after payload checks. The fixed experiment requires both receivers; OLSR requires one. Failure is preserved as a row.
- `completion_s`: latest required receiver completion minus first offer, only when all required receivers finish. Otherwise the field is empty. `completion_goodput_bps = 8 * useful_bytes / completion_s`, also missing for failed completion. This finite-transfer rate is not a capacity estimate.
- `window_goodput_bps = 8 * useful_bytes / (deadline_s - offer_s)`: includes partial useful delivery and uses the full configured application window.
- `transfer_frames/bytes`: every frame started after offer through simulation end. `data_*`, `control_*`, and `routing_*` partition those totals. TCP segment sizes and callback boundaries do not define original application packets. Frame comparisons depend on MSS and headers; compare bytes and the category breakdown as well.
- `central_frames/bytes`: actual directed device traffic from node 3 to node 4 only in the known butterfly. Reverse ACKs are counted elsewhere in overall traffic. Blank for arbitrary random graphs where there is no designated central link. `central_rate` names the configured rate in that fixture, not a bottleneck discovered in a random graph.
- `phy_rx_drops`: receive-error drops observed at devices after offer. `injected_app_drops` and `validation_drop` describe the separate controlled application-discard fixtures. They must not be treated as channel errors.
- `xor_operations`: actual XOR-combination executions, rather than a routing decision or a count of packets forwarded in a butterfly role.

The CSV records source/destinations, graph seed, ns-3 RNG seed/run and scenario identifiers. Pilot manifests record all CLI parameters, source hashes, ns-3 commit, compiler and platform. Per-link receive-error streams are explicitly assigned (2000 + device index); methods share stream assignments, not necessarily losses on corresponding application messages. A new CSV filename is required when an existing header differs. Older rate/goodput columns have been removed from collection rather than reinterpreted silently.

FlowMonitor is an optional **IP-layer diagnostic XML** when `tracePrefix` is provided. It does not supply application goodput or aggregate device traffic. Its loss check uses the configured cleanup interval, and potentially outstanding IP packets must be interpreted with that bound. See the [official scope and limitations](https://www2.nsnam.org/docs/models/html/flow-monitor.html) and the installed 3.44 source in `src/flow-monitor/doc/flow-monitor.rst`.

## Validation and limits

`python3 test/validate-correctness.py` checks deterministic field/decoder correctness, known OLSR XOR/payload behavior, and fixed-butterfly data/ACK counts. The no-loss device totals are cross-checked against independent PCAP parsing: each successful frame is captured at transmission and reception. The NC byte oracle is 9 × (1024 payload + 19 NC header + 8 UDP + 20 IP + 2 PPP) data bytes plus 9 × (15 ACK + 8 UDP + 20 IP + 2 PPP) control bytes. Prescribed data and ACK discards recover with exactly one retry; total loss exhausts the configured retry budget. These are fixture checks, not validation of every loss/routing regime.

Fixed NC now enforces the supported one-generation setting (two originals, generation size two, unfragmented packet sizes). It uses a bounded retry count and suppresses duplicate forwarding while still acknowledging duplicates. TCP offers the same two original payload patterns to each receiver at the same start time, handles send-buffer backpressure, and verifies the stream bytes. TCP uses ns-3.44 defaults (TcpCubic and default segmentation/recovery settings); the pilot pins the version, not a universal Internet TCP configuration.

The unicast OLSR selection heuristic still omits the ingress cost when comparing exit distance with the traditional route. Do not interpret its decision as an optimality or cost-benefit proof. An uncoded forwarding baseline with matched reliability is still needed to attribute differences specifically to coding. Random-graph disconnected/reselection accounting and systematic scalability tests remain to be completed before the full main study.
